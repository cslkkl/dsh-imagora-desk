# 任务池补上终态 TTL

状态：生效

## 问题

插件早期照搬了原版的任务池，但只搬了数量上限（`MAX_KEEP = 200`），没搬
`TERMINAL_TTL_SECONDS = 600`。后果：跑完的任务对象一直留在内存里，连同它的
`mask` Buffer —— 那是**原图尺寸的 PNG**（3072×4096 时几 MB），要等到被下一次提交
按数量挤掉才释放。开一整天、中途用过蒙版时，这部分是纯泄漏。

## 决策

按上游 `core/tasks.py` 的语义逐条对齐：

- `MAX_TASKS = 500`、`TERMINAL_TTL_MS = 600 * 1000`（常量名与注释都指向上游）。
- `trim()` 分两段：**先清超 TTL 的终态，仍超上限再清最旧的终态**（顺序与上游一致）。
  只看数量的话，攒到 500 条才清；只看 TTL 的话，一次提交几百个任务时上限形同虚设。
- `snapshot()` 里做一次惰性清理：轮询是唯一的高频入口，因此在**这里**清就够，
  不需要引入后台定时器（没有轮询、没有新提交的进程本来也不会再增长）。
- 删任务时显式 `task.mask = null`：进程里唯一还引用那个 Buffer 的就是任务对象，
  不显式断开就要等 GC 兜底。

## 替代方案

- **只加 TTL、保留 200 上限**：批量提交几百个任务时仍是硬顶，且与上游数字不一致。
- **后台 `setInterval` 定期清理**：多一个需要生命周期管理的定时器；惰性清理的覆盖面
  已经被「提交时 + 轮询时」两个入口覆盖。
- **跑完立刻删任务**：前端轮询拿不到终态快照，「结果回流」会丢——TTL 的 600 秒正是
  给轮询留的窗口，不能省。

## 影响

- 内存不再只增不减；蒙版 Buffer 在任务被清时立刻可回收。
- 行为可见变化：一个任务结束 10 分钟后再来轮询，会拿到 404（前端按既有逻辑收尾成
  「任务已丢失，重新运行即可」）——与上游同一语义。
- 新增 6 条 host 冒烟断言：终态超 TTL 被清、清任务时释放蒙版、运行中/排队中不受影响、
  超上限清最旧终态、轮询到过期任务返回 null、惰性清理也释放蒙版。
